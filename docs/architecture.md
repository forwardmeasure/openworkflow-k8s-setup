# Architecture

## Design goals

1. Both OpenWorkflow engines deploy to the same cluster without owning shared
   operators or copying secrets across namespaces.
2. Workload charts remain cloud-neutral. Cloud identity and managed-service
   details terminate at External Secrets and ordinary Kubernetes Secrets.
3. Provider infrastructure and portable Kubernetes bootstrap have separate
   state and lifecycle boundaries.
4. Versions are pinned and upgrades are deliberate.

## Platform shape

```text
Internet -> reserved provider IP -> Istio Gateway -> HTTPRoutes
                                      |-> Keycloak
                                      |-> Kafka Streams APIs/Studio
                                      `-> Actor Engine API/Studio

GKE workloads -> External Secrets -> Google Secret Manager
             |-> private Cloud SQL PostgreSQL
             `-> Strimzi Kafka (cluster internal)
```

Runtime namespaces use Istio sidecar injection and strict namespace-scoped
mTLS. Operator namespaces and stateful platform services do not receive
sidecars by default; this avoids bootstrap deadlocks and keeps Kafka and
Keycloak lifecycle independent of application mesh policy.

## Portable contract

The bootstrap promises these stable Kubernetes-facing resources:

| Resource | Contract |
|---|---|
| Gateway | `istio-system/platform-gateway`, HTTPS listener `root-https` |
| Secret store | `ClusterSecretStore/google-secret-manager` on GCP |
| Kafka | `kafka/kafka-cluster`, bootstrap service `kafka-cluster-kafka-bootstrap:9092` |
| OIDC issuer | `https://auth.<root-domain>/realms/openworkflow` |
| Actor database secret | `openworkflow-actor-engine/openworkflow-database` |
| Kafka Streams DB remote keys | IDs emitted by Terraform and consumed by its prerequisites chart |
| Monitoring labels | `release: kube-prometheus-stack` |

The name `google-secret-manager` is currently consumed by the Kafka Streams
greenfield example. In later providers, engine environments should select the
provider's store name rather than assume it globally.

## GCP decisions

- Regional Standard GKE with separate system and workload node pools.
- VPC-native pods/services, private nodes, Cloud NAT, Workload Identity, and
  Shielded Nodes.
- Cloud SQL PostgreSQL on a private service networking address.
- Secret Manager values are generated by Terraform. They therefore exist in
  Terraform state; the remote backend must be encrypted and tightly access
  controlled.
- External Secrets uses a dedicated Google service account linked to its
  Kubernetes service account. No JSON service-account key is created.
- A regional static address is reserved for the Istio-managed Gateway service.

## AWS and Azure sequence

The next provider stacks should implement the same outputs rather than fork the
bootstrap:

| Capability | GCP | AWS | Azure |
|---|---|---|---|
| Kubernetes | GKE | EKS | AKS |
| PostgreSQL | Cloud SQL | RDS/Aurora PostgreSQL | Azure Database for PostgreSQL |
| Secrets | Secret Manager | Secrets Manager | Key Vault |
| Pod identity | Workload Identity | EKS Pod Identity/IRSA | Workload Identity |
| Public address | regional address | NLB allocation/annotation | Public IP resource |
| Object storage (future) | GCS | S3 | Blob Storage |

Only the External Secrets provider configuration, cloud load-balancer
annotations, and Terraform stack should differ. The shared Helmfile releases,
Gateway, namespaces, Keycloak realm contract, and Strimzi cluster stay common.

## Deliberate exclusions

- DNS delegation and records, because the authoritative zone is not always in
  the workload project/account.
- Application image publication and image digests.
- Tenant creation and workflow-specific endpoint authorization.
- Cassandra. It remains a supported actor-engine persistence profile, but the
  initial shared platform standard is managed PostgreSQL.
- Production backup/restore automation and disaster-recovery replication;
  those require environment-specific retention and recovery objectives.
